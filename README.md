## **Повторение приципов SOLID**

**Постановка задачи:**
Предложены архитектурные решения классов некоторых приложений. Необходимо найти в этих решениях несоответствия принципам SOLID и предложить исправленные решения. Решение должно быть в виде CLI.

#### **Описание принципов SOLID**
* **S - Single Responsibility Principle** — принцип единственной ответственности. У класса должен быть только один мотив для изменения.
* **O - Open/Closed Principle** — принцип открытости/закрытости. Класс может быть расширен, но не может быть изменен.
* **L - Liskov Substitution Principle** — принцип подстановки Лисков. Функции, которые используют ссылки на базовые классы, должны иметь возможность использовать объекты производных классов, не зная об этом. Объекты наследников должны корректно заменять объекты базового класса.
* **I - Interface Segregation Principle** — принцип разделения интерфейсов. Клиенты не должны зависеть от методов, которые они не используют. Лучше несколько маленьких специализированных интерфейсов, чем один большой.
* **D - Dependency Inversion Principle** — принцип инверсии зависимостей. Классы верхних уровней не должны зависеть от классов нижних уровней. Оба должны зависеть от абстракций. Абстракции не должны зависеть от деталей. Детали должны зависеть от абстракций.

#### **1 задача. Валидация данных**

**Проблема:** В классе Product имеется логика по валидации введенных данных, хотя класс Product должен содержать характеристики товара и методы для работы с этими характеристиками.

- Нарушен Single Responsibility Principle.

**Решение:** Вынести логику по валидации введенных данных за границы класса. Это можно реализовать при помощи отдельного класса, отвечающего за отдельный вид валидации, но это может нарушить Open/Closed Principle - мы не сможем расширять класс для валидации. Поэтому следует, помимо вынесения логики по валидации в отдельный класс, сделать абстрактный класс - интерфейс. Через интерфейс мы сможем передавать любой кастомный валидатор в конструктор класса Product.

#### **2 задача. God object**

**Проблема:** В классе ImageHelper имеется логика самым разнообразным действия над изображениями: работа с ФС, работа с профилями пользователей, изменение свойств изображения, загрузка изображений из интернета. У класса как минимум 4 ответственности. Класс будет очень часто изменяться - это тонкое место архитектуры этого класса.

- Снова нарушен Single Responsibility Principle.

**Решение:** Вынести каждую ответственность в отдельный класс.

#### **3 задача. SMTP Mailer**

**Проблема:** В классе SMTPMailer используется логгер. Класс SMTPMailer зависит от конкретной реализации Logger. Если нам нужен будет другой вид логгера, то придется делать изменения в классе SMTPMailer. Это нарушает принцип открытости/закрытости. Класс SMTPMailer будет модифицироваться каждый раз, когда будет добавляться новый вид логгера. Но следует отметить, что принцип Single Responsibility Principle был соблюден.

- Нарушен Open/Closed Principle.

**Решение:** Добавить интерфейс логгера. Каждый новый вид логгера должен реализовывать этот интерфейс. В SMTPMailer передавать абстрактный класс.

#### **4 задача. Repository**

**Проблема:** Класс Repository, реализует метод Save, действия в Save зависят от того, какая сущность используется. Если возникнет новая сущность, то придется менять Repository. Также в иерархии классов самый верхний уровень (Repository) зависит от низкоуровневых сущностей (RoleEntity, AccountEntity).

- Нарушен Open/Closed Principle и Dependency Inversion Principle.

**Решение:** Сделать из AstractEntity интерфейс (в нем задаем абстрактный метод Save), наследники AstractEntity должны определить метод Save. Метод Repository принимает интерфейс --> Repository становится открытым для расширения и закрытым для изменений, также пропадает зависимость от низкоуровневых сущностей.
